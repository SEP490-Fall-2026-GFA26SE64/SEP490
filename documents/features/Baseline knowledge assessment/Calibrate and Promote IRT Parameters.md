## Selected numerical package — simulation only

This is an authorized engineering demonstration. The numbers are not a universal sample-size or psychometric-quality standard. Actual execution and admission results must be recorded separately; selecting this package does not imply convergence or a candidate exists.

Implementation precision selected before algorithm code: Java21 SplittableRandom/StrictMath Box–Muller (u1=1-nextDouble), seed20261022; sorted skill IDs and item-version UUID strings, generating item parameters first then subject abilities/options. Estimator initialization a=1,b=0, no item prior and no generating-parameter input. Bounded projected Newton M-step with analytic gradient/Hessian and scaled-gradient fallback, at most50 steps/item/EM and20 backtracking evaluations/step; inner max parameter change1e-6, objective ascent only. Quadrature weights are normalized exp(-theta²/2) at41 equally spaced points[-5,5]. Pattern aggregation is exact for complete nine-item matrices. Relative likelihood change uses denominator1+abs(previous likelihood); decrease tolerance1e-8; boundary rejection within1e-5. One run has at most10,000,000 objective evaluations in addition to the wall-time/interruption/input bounds. All precision choices are hashed in algorithm configuration, not production model defaults. One deterministic initialization gives a local optimum only; no global-maximum or uncertainty claim.

- Formula: P(correct)=c+(1-c)logistic(a(theta-b)), D=1. Separate unidimensional fits per exact MicroSkill; population theta distribution fixed N(0,1). This population identification assumption is distinct from the runtime learner MAP prior.
- Estimation: marginal maximum likelihood by EM, deterministic 41-point rectangular normal-weight quadrature on [-5,5]. Fit a in[0.25,3] and b in[-3,3]; **fix c=.25**, with `estimated=false` diagnostics. Do not describe fixed c as fitted. A fully estimated 3PL is an alternative needing a separate agreement.
- M-step uses the bounded projected Newton procedure frozen above; no numerical library/package or external service is introduced.
- Generate2,000 synthetic subjects per skill, each answering all9 item versions in that skill:270,000 observations total. Seed20261022 with a versioned Java PRNG and normal transform. Generating a~Uniform(.7,1.8), b~Uniform(-2,2), c=.25, independently of difficulty/Level/content. Each subject-skill ability~N(0,1); conditional responses Bernoulli(P). Wrong option chosen from the other presented options. These are synthetic subject tokens, never platform account/learner IDs.
- Keep generating parameters/abilities in a separately hashed synthetic sidecar. The estimator receives only pinned item/skill identities and observed responses; no generating theta or a/b leaks into fitting. Candidate contains fitted a/b and explicitly fixed c. Synthetic recovery comparisons are descriptive, not real-user validity.
- First version requires a complete matrix per skill: reject missing/duplicate observations, unknown options/items, mixed versions/skills and client-supplied correctness. No missing-as-wrong, imputation, adaptive-selection-bias correction or automatic import of historical attempts. Actual pilot missingness/design needs separate alignment.
- Maximum200 EM iterations/skill. Selected convergence: relative log-likelihood change≤1e-6 and max absolute a/b change≤1e-3 for3 successive iterations; unacceptable likelihood decrease/nonfinite/bound hit/nonconvergence rejects the whole candidate. Precision is frozen in CalibrationPolicy and the implementation paragraph above.
- Selected hard limits: one worker,300 seconds computation budget/run,64 MiB dataset input,≤1,000,000 observed responses,≤5,000 subjects/skill and exactly the pinned135 items/15 skills. Parser bounds include nesting16, string4000, numeric token64 characters and2 million tokens. Input-file I/O and cleanup have their own bounds; a 300-second compute budget is not a hard operating-system kill guarantee. The observed offline CLI used Xmx256m/ActiveProcessorCount1; service CPU concurrency is serialized across instances by a PostgreSQL session advisory lock outside long transactions.
- Selected minimum per item:1,000 observations and at least50 correct/50 incorrect. Complete finite coverage and convergence required for all135 tuples. These are demo admission limits, not evidence that nine items establish a valid skill instrument.
- Run/item diagnostics: origin, input/algorithm/code/seed/generator/model/content hashes, counts/options/coverage/missingness, status/reason, likelihood trace summary, iterations/evaluations/time, bounds/degenerate items, empirical proportions, predicted-marginal residuals and explicitly named fit summaries. No invented p-values or standard errors. Parameter uncertainty/SE remains unavailable until an approved and verified method exists. Synthetic parameter/curve recovery belongs in the synthetic sidecar.
- SUCCEEDED means the agreed computational/admission contract completed; it never means expert approval or production validity. A SYNTHETIC candidate remains ineligible for operational promotion under this proposal. Its V18 source may be CALIBRATED only with origin=SYNTHETIC repeated in sealed run/candidate diagnostics and protected from being hidden by a source-only projection.

Primary references support the method family and caution, not these proposed constants: [mirt author's documentation](https://philchalmers.github.io/mirt/reference/mirt.html) describes EM/grid integration and explicit item-model constraints. [ETS RM-23-03](https://www.ets.org/Media/Research/pdf/RM-23-03.pdf) examines sample-related parameter uncertainty and lower-tail recovery limitations. No R service/library is introduced: production backend remains Java21/Spring Boot3.5.

## Proposed C1 contract and ordered operations

Ports: trusted calibration authorization; authorized immutable dataset source; bank/model snapshot reader; pure calibration engine; transactional run/candidate persistence/query. Application records contain typed values, never JDBC rows, entities or another owner's DTOs. Exact names/wire DTOs remain design, not existing APIs.

Client command supplies run UUID/idempotency identity, dataset reference/hash, bank/release hashes, exact model ID/configuration hash and approved algorithm-config hash. Server supplies authenticated actor/organization, bank/model grant, authoritative content/option/answer snapshots, computed request/input/parameter hashes and DB timestamps. Reject arbitrary remote file/HTTP dataset access; accept only a server-authorized immutable source reference. Raw responses, protected keys, generating abilities and full manifests are absent from ordinary API output/logs.

1. Authorize before existence/query results, including GET/replay; verify active organization and bank creator ownership boundary plus actual owner grants. Missing identity/source/model/permission fails before a run write. DRAFT content can be inspected for explicitly authorized isolated simulation, never admitted to Employee runtime by this path.
2. Preflight exact immutable dataset bytes, origin, shape, options, all135 item-version+skill+content-hash tuples, ontology/scope/manifest hashes and model configuration/artifact pins. Strict duplicate/unknown-field/trailing-token/numeric/size validation. Never rewrite historical correctness.
3. Short serialized transaction: reauthorize, recheck pins, reserve run UUID as V18 PENDING. Configuration includes schema version, trusted actor/org/bank scope, canonical request hash, provenance and agreed limits. Same identity/hash returns owned state; changed body/scope conflicts. Do not invent a second row for an uncertain commit.
4. Claim PENDING→RUNNING in a short compare-and-set transaction. Persist started_at and a bounded worker token/deadline in diagnostics. Only the claiming worker may complete. Run compute outside a long database transaction, with explicit memory/evaluation/time/cancel bounds. No startup or request automatically launches simulation.
5. Timeout/cancel/dependency/numerical/coverage failure: one short transaction changes owned RUNNING→FAILED with sanitized reason/completed_at, no output set. V18 has no CANCELLED state: use FAILED plus reason. Crash recovery claims only expired work under lock and marks FAILED; never silently resets RUNNING to PENDING or overwrites terminal history. A deliberate retry has a new run identity linked to the previous one; exact retries retain the old outcome.
6. Success: one transaction rechecks authorization, exact pinned model/content, worker ownership and deadline; computes canonical parameter hash; inserts set BUILDING/source CALIBRATED and all135 immutable exact tuples/fit_diagnostics; seals CANDIDATE; changes run RUNNING→SUCCEEDED with output set and complete diagnostics. Any failure rolls back candidate/item/run completion together; no partial candidate. A rollback that leaves RUNNING is reconciled by owned failure/recovery, preserving uncertain-commit checks.
7. Query returns only the authorized run/candidate scope, safe diagnostics and parameter summary. Empty/not-found/foreign/dependency errors remain distinct internally and safe externally. Reads create no receipts/status changes or recovery writes.

V18 map: run.input_dataset_ref is the authorized content-addressed reference; run.configuration is immutable request/provenance/policy; run.diagnostics records bounded progress/final outcome; output_parameter_set_id links the sealed output; set.parameter_hash binds exact scope/input/model/algorithm/tuples/diagnostics; item.fit_diagnostics binds each tuple and origin. Envelope also snapshots the existing model algorithm/version/parameter hash/canonical configuration hash/artifact_ref and real approval pair, without new columns or invented approvals. Configuration hash is recursive canonical JSON of the stored configuration, not a typed record with potentially normalized number spellings. No new calibration columns are introduced. A model_version FK must exist; the current empty model table prevents persisted execution until the model input is explicitly resolved.

## Proposed C2 contract, scope and atomicity

Authorization is a separate trusted owner port. No HTTP request may submit actor/org/role/admin=true; no configured fake Admin, role-code alias inference or local-seed exception. Reauthorize reads/replay and promotion under the owner's revocation/locking contract. System Administrator must have the exact organization+bank+model grant. L&D, Employee, inactive, foreign and unknown contexts are denied. Until owner integration exists, register no enabling route/bean and retain default deny-all; no fabricated principal or permission migration.

Promotion command: candidate ID/hash, exact model configuration hash, expected effective revision and expected current parameter-set ID or explicit none, plus idempotency key/reason. Server derives scope from trusted context and sealed run; it never trusts candidate IDs alone. First promotion explicitly expects revision0/none. A new key cannot repromote an already promoted historical set or make it current again.

V18 permits multiple immutable historical PROMOTED rows; V23 supplies the missing effective bank/tenant pointer and typed promotion receipt. V23 is now applied locally, with source/history checksums verified on23 October2026. Operational calibration/promotion remains separately gated:

- Scoped effective selection keyed by(organization_id,question_bank_id,model_version_id), pointing to exact(parameter_set_id,model_version_id), with monotonic revision and actual actor/time. Verify ownership against the real bank/account/model contracts; no inferred global grant.
- Append-only promotion command receipt keyed by(organization_id,actor_id,idempotency_key), containing exact bank/model/candidate/request hash, expected selection and original safe outcome. Do not overload Blueprint operation checks, event-processing receipts or sealed run diagnostics.
- Keep V1–V22/triggers/old rows unchanged. Reuse audit_event for a real promotion action if owner audit contract permits it. No deletion or demotion of historical PROMOTED sets.

Frozen source schema for V23: `irt_effective_parameter_selection` has organization_id,question_bank_id,model_version_id (PK),parameter_set_id,selection_revision,selected_by,selected_at. `irt_parameter_promotion_command` has organization_id,actor_id,idempotency_key (PK),question_bank_id,model_version_id,request_hash,parameter_set_id,parameter_hash,expected_revision,expected_parameter_set_id,selection_revision,reason,occurred_at. The original typed Selection response is reconstructed from immutable columns; no arbitrary JSON response/schema field is required. Receipt(scope,selection_revision) is unique. FK/triggers preserve actor organization, exact model/set, monotonic pointer revisions and matching append-only receipt; eligibility additionally requires the successful actual-pilot originating run/model approval and owner readiness checks. This migration is not to be applied to main during Session2.

Atomic ordered command: authorize → serialize exact selection scope (including absent pointer) → lock/recheck actor/grants, bank/model/candidate and successful originating run → exact authorized receipt replay before current-revision checks → reject new stale command → recompute candidate hash/full exact coverage/diagnostic admission/input provenance/model approval/review prerequisites → CANDIDATE→PROMOTED plus pointer revision+1 plus immutable receipt/audit in one commit. Any failure rolls back all promotion metadata. SYNTHETIC/unreviewed/incomplete candidates fail the proposed operational eligibility gate. No automatic promotion during run completion.

Two commands expecting the same revision: one succeeds, the other conflicts; identical key/body returns the original outcome after reauthorization even after a later promotion. Changed body/scope/key reuse conflicts. Unknown commit: retry the identical command, never allocate another candidate or rewind the pointer. Statement/lock timeouts are bounded; safe retry follows receipt reconciliation.

Future selection requires a scoped technical port, joining the effective pointer and successful sealed run scope. No fallback to newest global PROMOTED. At future Blueprint Activate, hold/recheck selection through commit so promotion and new-version pinning have a clear serialization order. Existing/pinned findPinned and attempt/result readers remain exact and do not consult the effective pointer. Promotion changes no existing Blueprint, attempt, scoring, evidence, completion, allowance or Role selection. The runtime call-site change is C2 selection integration only; broad Compose/routes cleanup remains Session3.

V23 is applied; trusted operational Identity/readiness/dataset ports still have no enabling implementation/default. Operational persistence stays unwired/denied until actual owner integration exists; Admin success/races remain unobserved. Current C1 supports the agreed synthetic design only: an actual-pilot estimator/data policy requires separate alignment before an operationally eligible candidate can exist.
