### Platform organization directory projection (2026-11-04)

`GET /api/v1/platform/workspaces` retains `organizationId`, `name`, administrative `status` and provisioning `setupState`. Its read-only extension adds `subscription: { status, current }` and `administrators`. `current` is null outside an active paid period; otherwise it exposes only the purchased plan `name`, `startsAt` and `endsAt`. Coverage uses one server instant and half-open periods `[startsAt, endsAt)`: ACTIVE for current coverage, SCHEDULED for future-only coverage, EXPIRED for historical coverage without a current/future period, and NONE when no paid period exists. These states do not derive from administrative suspension.

Administrators are current `ORGANIZATION_ADMINISTRATOR` membership-role assignments, not a permanent designation of the original registrant. Each projection contains `accountId`, nullable `fullName` (current profile, then legitimate registration-name fallback), `email`, membership `active` and `accountActive`; inactive assignments remain visible. Missing assignments produce an empty list. Organization, account and membership tenant IDs must match. Two batched JPA projections load administrator display data and paid-period display fields for the provisioned organization IDs; no tenant billing/history API is reused or newly authorized.

The existing trusted platform guard, no-store response and suspension transaction/audit remain the owners. `PUT /api/v1/platform/workspaces/{organizationId}/suspension` requires a non-null boolean `suspended` plus existing session/CSRF authorization; missing/null intent is rejected rather than defaulting to reactivation. Confirmation occurs in the UI, not as a substitute for server authorization. Reactivation changes only administrative status, never paid dates or setup readiness. No profile-write endpoint, storage/schema migration or new dependency is introduced. [API/persistence evidence](testing/integration/REQ-064-manage-organizations-20261104.md).

The backend follows a layered architecture rooted at `com.adaptlearngraph`. Requests flow `apis` (controllers, routes from `endpoints`, failures mapped by `advice`) -> `services` (business logic; use-case interfaces such as `TargetRoleQueryUseCase` and their implementations) -> `repository` (data-access contracts such as `TargetRoleCatalogPort`, Spring Data repositories and their JPA/SDN adapters) -> `entities` (persistence mappings) and `entities.domain` (immutable domain models). Infrastructure packages (`config`, `constants`, `exception`, `helper`, `jwt`, `utility`) support every layer. Subscription/payment capabilities are required by Version 2 but not established by this baseline. Prototype screens/stores do not prove persisted onboarding, payment, authorization or learning workflows.

## Persistence layer (ORM, 2026-11-03)

PostgreSQL and Neo4j access goes through Spring Data; hand-written JDBC/driver adapters were replaced domain by domain without schema or API changes.

- **Schema ownership:** Flyway (all three lineages) remains the only source of the PostgreSQL schema. Hibernate runs with `ddl-auto: validate`; `JpaSchemaValidationIntegrationTest` boots the mappings against each lineage. Domain-typed columns use `PostgresColumnTypes` (`content_hash`, `unit_interval`), `jsonb` uses `@JdbcTypeCode(SqlTypes.JSON)` and `text[]`/`uuid[]` use `@JdbcTypeCode(SqlTypes.ARRAY)`. Triggers, constraints and functions stay in the database and are not re-implemented in Java.
- **Mappings:** `entities/*Entity` are mutable JPA mappings (`@DynamicInsert/@DynamicUpdate`, owner/tenant columns `updatable = false`, append-only and trigger-frozen tables `@Immutable`) without business validation; `entities/*Node` are SDN read models. The validated immutable domain model lives in `entities.domain`.
- **Repositories and tenant isolation:** organization-owned repositories extend Spring Data `Repository` (+ `InsertOnlyRepository` for persist-and-flush inserts), never `JpaRepository`/`Neo4jRepository`, so there is no unscoped `findById`/`findAll`/`save`/`delete`; every method takes the organization id. `RepositoryTenantSurfaceTest` enforces this for JPA and SDN repositories, and per-domain integration tests prove organization B cannot read or write organization A's rows or nodes.
- **Native SQL kept on purpose** (each query carries a reason comment): `FOR UPDATE [OF ...] [SKIP LOCKED]`/`FOR SHARE` row locks (lock ids natively, then read through a JPQL projection), fenced lease updates for workers, `ON CONFLICT` idempotency and seeds, `clock_timestamp()`/`now()`-based scheduling, `DISTINCT ON`, `LATERAL`/`jsonb` path filters, `set_config` (`SET LOCAL`) timeouts and `SET CONSTRAINTS ... IMMEDIATE`. Advisory locks go through `PostgresAdvisoryLocks`; unique violations through `PostgresErrors`. `JdbcCalibrationWorker` keeps one dedicated JDBC connection because its session-level `pg_try_advisory_lock` must outlive transactions.
- **Neo4j:** reads use `@Node` models, scoped SDN repositories and `Neo4jClient`; writes follow projection-save — `Neo4jTenantGuard` rejects ids owned by another (or no) organization, nodes are written with `MERGE`/`SET` Cypher, and relationship writes match both endpoints in the same organization. Catalog copy (`Neo4jWorkspaceCatalogWriter`) keeps deterministic ids and `UNWIND` batching through `Neo4jClient`. `Neo4jQuestionBankSkillReader` keeps the driver's async session so a stalled graph call cannot hold the caller's PostgreSQL transaction past its deadline.
- **Transactions:** `transactionManager` (JPA, primary) and `neo4jTransactionManager` (SDN) are named in `constants.TransactionManagers` and always selected explicitly; there is no chained transaction manager. Cross-store flows keep their existing order and compensation steps.
- **DTO mapping:** `config.ModelMapperConfiguration` builds one STRICT ModelMapper (`helper.ModelMapperFactory`: record module, `skipNull=false`, `validate()` at startup) from `helper.*Mappings` registrars with explicit TypeMaps/converters. Writes construct domain commands explicitly; organization, ids, revision, status and reviewer fields come from the path or trusted session, never from request bodies. Mapping tests assert that password hashes, TOTP secrets, tokens, payment signatures, request hashes, worker tokens and answer keys outside existing reviewer endpoints never appear in DTO JSON.

## Implementation Decisions

1. **Catalog history and isolation:** Map stable graph IDs to PostgreSQL `catalog_reference` (`entity_id`, `version_id`, `release_id`), pin attempts/pathways to valid versions, and design organization ownership for every traversal and projection. Dataset uniqueness constraints alone do not provide tenant isolation.
2. **Commercial lifecycle:** Specify registration, email verification, versioned purchase/renewal, seat allocation/counting, workspace suspension/expiry and idempotent provisioning. Plan updates must not silently rewrite previous purchases. Cancellation is not a confirmed product function.
3. **Identity and organization structure:** Migrate legacy actor codes explicitly to the six-actor model without privilege expansion; design memberships, department deletion/reassignment history, job position-department references and Expert assignment enforcement.
4. **Catalog and content governance:** Specify completion/publication/return states, many-to-many module/skill coverage, versioned approval, private MinIO delivery and withdrawal effects. Retain legacy `sourceUrl` and dataset `contentUri` meanings until a forward mapping is approved.
5. **Assessment and adaptation:** Define baseline/module/RIASEC rules, mastery and gap calculations, local-LLM inputs/failures, initial Expert confirmation, recalculation and override preservation. No mandatory Expert AI-guidance review or failure-only adaptation.
6. **Reporting and audit:** Define employee/department aggregation, costs/benefits attribution, ROI calculation, zero-cost/mixed-currency behavior, event retention and notification delivery policies.
7. **Deployment and verification:** Implement the Nginx/GitHub Actions target and external integrations; choose HTTPS/domain, secret handling, backups and monitoring. Test complete workflows and isolation with at least two demo organizations. Preserve historical evidence; new requirements need new unit/integration/system evidence rather than relabeled passing runs.

### Commands and consistency

Trusted session/membership/workspace entitlement resolves actors; only same-organization DOMAIN_EXPERT/LD_MANAGER may use the bank API. Commands recheck active membership/role under transaction locks. Per-organization advisory serialization plus expected question revision prevents competing writes. Only responsible Expert edits/submits/withdraws; peers read. L&D assigns/transfers with reason, reviews/returns, confirms retirement/reactivation. Submitted content is immutable; returning/withdrawing invalidates review acknowledgement. Transfer retains exact submitted content and original submitter.

L&D acknowledgement is tied to the submitted version. Approval atomically publishes that complete version; bulk approval validates all selected versions first and rolls back every decision on any failure. New complete versions project into existing `item_version` using protected A–D key/response schema and content hash; existing legacy DRAFT rows can publish only after authorized repair/review. Existing PUBLISHED rows remain immutable. Explanations/audits remain staff-only authoring data; no change to Employee answer-release policy.

A successor is a new candidate version; old published content remains eligible while it is draft/submitted. Approval does not replace pins or promote model parameters. Confirmed retirement disables the stable question across versions for future selection; pinned historical assessment/attempt definitions remain intact. Reactivation is explicit, validates current eligible published content and never publishes a draft.

Import uses .xlsx/JSON template columns without `code` and only creates new drafts. Each valid preview row receives a unique backend-generated `Q-<uppercase UUID>` code persisted in the preview; confirmation reuses that code and a committed receipt makes replay idempotent. Existing questions/versions are never updated by file import. New-only previews carry `generatedCodes=true`; old pending previews lacking this marker or carrying update expectations require a fresh upload. This additive field lives in the existing PostgreSQL JSON aggregate, not Neo4j; no SQL migration is needed. Code-bearing files are rejected with latest-template guidance. Normalized prompt plus four options still warns about matching content (including within the file), requiring explicit acknowledgement. Current skill eligibility and changed duplicate-content conditions are rechecked on confirm; any invalid row prevents the whole batch. Default limits10MiB/500 rows remain configurable. Edit/successor commands use existing question IDs and preserve their original codes.

Notifications are persisted with question mutation; email jobs are independent. SMTP failure does not roll back question decisions. Worker locks/leases jobs, checks current same-organization active staff recipient, retries then records failure, uses stable Message-ID; exactly-once email delivery is not claimed. Acceptance sends only to the isolated local Mailpit.

Commands serialize with an organization advisory transaction lock and Module row lock; expectedVersion prevents stale writes. A submitted package is not editable. Graph and PostgreSQL are not a distributed transaction; learning admission uses PostgreSQL's released receipt, not a graph status alone.

Draft/revision/audit/Job Position membership do not add graph properties. Archive projection preserves the pinned payload in PostgreSQL; restore creates a draft and requires approval.
